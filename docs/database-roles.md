# PostgreSQL roles: administrator and application login

Since this change the API no longer connects to PostgreSQL as a superuser
([issue #52](https://github.com/VardrSec/VardrSec/issues/52)). Two roles exist in the
`vardrmap` database of the Compose installation:

| Role | Privileges | Used by |
| --- | --- | --- |
| `vardrmap` (administrator, from `POSTGRES_USER`) | Superuser | Only inside the database container: `database-role`, backup (`pg_dump`), restore (`pg_restore`), integrity fingerprints. Its password (`POSTGRES_PASSWORD`) is never given to the API |
| `vardrmap_app` (application) | Plain login: no SUPERUSER, CREATEDB, CREATEROLE, REPLICATION or BYPASSRLS, no role memberships | The API: requests and the unchanged `alembic upgrade head` at startup. It owns the application tables and has `CREATE` on schema `public` only |

The application role cannot run `COPY ... PROGRAM`, read server files, change server
settings, create roles, databases or schemas, or become the administrator. It can still
change its own tables, which migrations require; a separate migration account is
deferred (Phase 2). Map's tenant isolation is application-level (the database uses no
row-level security); because table owners are exempt from row-level security, adopting it
later needs `FORCE ROW LEVEL SECURITY` or the Phase 2 split.

Its password is `POSTGRES_APP_PASSWORD` in `.env` (generated by `configure`, never
displayed). PostgreSQL receives only a SCRAM-SHA-256 verifier of it, and statement logging
is disabled for the session that sets it.

## New installation

`python3 vardrsec.py install` runs `database-role` after `build` and before `start`. Nothing
else is needed.

## Existing installation (persistent database volume)

An installation made before this change keeps its data owned by the administrator and has no
application role. After you update the checkout, Compose refuses to start until the role
exists (`POSTGRES_APP_PASSWORD` is required). The upgrade changes only role attributes and
table ownership: no row is rewritten, and the administrator and its password are untouched.

1. **Back up with the version you are running now**, before updating the checkout (the new
   Compose file refuses to run without `POSTGRES_APP_PASSWORD`, so `backup` fails until step 3). If you already updated, check out the
   previous commit, back up, then return:
   `python3 vardrsec.py backup --destination DIR`. Applications stay stopped afterwards.
   Do not change data between the backup and step 3.
2. Update the checkout.
3. `python3 vardrsec.py database-role --backup DIR`. It refuses unless the backup validates
   and its database fingerprint equals the current database, and refuses while `api`, `web`
   or `proxy` run. It adds `POSTGRES_APP_PASSWORD` to `.env` if absent (value not shown),
   applies one transaction, then logs in as the new role over the network and verifies it.
4. `python3 vardrsec.py start`.

Repeating step 3 is safe: with nothing to change it needs no backup and changes nothing
(the credential in `.env` is only ever added, never rewritten).

If the command fails, nothing is partly applied: the transaction rolls back and the
database still works for the previous configuration. Fix the cause and rerun it.

### Rollback

Restore the pre-change backup into a separate installation with `restore` (the backup
carries the old Compose file and `.env`, so it restores as a working pre-change
installation; acceptance proves this). To revert in place, run as the administrator inside
the database container, with the applications stopped and the previous checkout restored:
reassign tables back (`ALTER TABLE ... OWNER TO vardrmap` for each public table; sequences
owned by columns follow their table) and leave `vardrmap_app` in place, unused.

## Backup, restore and controlled updates

- Backups still use the administrator (`pg_dump --no-owner --no-acl`). A restore runs
  `pg_restore` as the administrator and then hands the restored data to `vardrmap_app`
  before any application starts; a backup from a pre-change installation restores unchanged
  as a pre-change installation and can be upgraded afterwards with `database-role`.
- Controlled updates are unchanged: the rehearsal is a restore, so it exercises the role
  hand-over. Running `update` or `backup` on an upgraded checkout whose `.env` lacks
  `POSTGRES_APP_PASSWORD` fails closed at configuration, before anything changes.
- Never put `POSTGRES_PASSWORD` into the API's environment.

## Evidence

`tests/database_role_acceptance.py` runs in the disposable Ubuntu 24.04 installation job:

- Fresh install: the API connects as `vardrmap_app`, migrations ran as that role, every
  public object is owned by it, its flags are all false with no memberships, it is denied
  `COPY ... PROGRAM`, `CREATE ROLE`, `CREATE DATABASE`, `ALTER SYSTEM`, `pg_read_file`,
  `pg_authid`, `ALTER ROLE ... SUPERUSER`, `SET ROLE vardrmap` and `CREATE SCHEMA` (all
  SQLSTATE 42501), it can run DDL on its own tables, a wrong password is rejected over the
  network, and the API environment holds no administrator password.
- Existing volume: a pre-change installation (old Compose file and `.env`, migrations run
  by the administrator, seeded account) is backed up, then upgraded. The upgrade is refused
  without a backup and with a stale backup, an injected mid-transaction failure rolls back
  completely, the real upgrade leaves the database fingerprint unchanged and the credential
  stable, a repeat is a no-op, the API reads the existing rows and reports migrations at
  head, and the pre-change backup restores.
- `recovery_acceptance.py` and `update_acceptance.py` run on top of the new role, and the
  restore assertions require the restored data to be owned by `vardrmap_app`.
